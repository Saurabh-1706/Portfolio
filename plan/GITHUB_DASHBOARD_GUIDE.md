# GitHub Analytics Dashboard — Implementation Guide

**Goal:** Show recruiters a live(-ish) picture of your GitHub activity —
repo stats, language breakdown, and a contribution heatmap — without
hammering the GitHub API on every page load.

**Placement:** A compact summary strip on the homepage (total stars,
current streak, mini heatmap) that links through to a full `/github` page
(complete 12-month heatmap, per-repo breakdown, language charts). Both
surfaces read from the same `GET /api/github/stats` endpoint.

**Stack note:** matches your current async SQLAlchemy 2.0 setup —
`app.core.database.Base`, not the sync-style `app.database.Base` used in
earlier scaffolding for this project.

---

## Phase 1 — Data Layer (this phase)

### 1.1 Why Postgres and Redis

- **Postgres (`repo_stats`, `contribution_days`)** is the durable source of
  truth. The sync job writes here. If Redis is ever flushed or cold after a
  deploy, Postgres is what the API falls back to — no data loss.
- **Redis** holds a single pre-aggregated JSON blob (the exact shape the
  frontend needs) with a TTL slightly longer than the sync interval. The
  public `/api/github/stats` endpoint reads from Redis only — this keeps
  every dashboard page load to a single fast cache hit, with zero GitHub
  API calls and zero Postgres aggregation queries on the request path.

### 1.2 Tables

**`repo_stats`** — one row per GitHub repository.

| Field | Purpose |
|---|---|
| `github_repo_id` | GitHub's own numeric ID — the upsert key, so re-syncing updates rows instead of duplicating |
| `name`, `full_name`, `description`, `url` | Display fields |
| `primary_language`, `languages` (JSON) | `languages` stores bytes-per-language, e.g. `{"Python": 48213, "TypeScript": 12044}` — lets you compute an aggregate language breakdown across all repos without re-calling GitHub |
| `stars`, `forks` | Self-explanatory |
| `is_private`, `is_fork` | Filtering flags |
| `is_featured` | Manually controlled — lets you exclude forks, throwaway repos, or private experiments from the public dashboard even if they technically sync. Default `True`; flip to `False` for anything you don't want recruiters seeing |
| `pushed_at`, `repo_created_at` | From GitHub, used for "last updated" and "active since" |
| `last_synced_at` | Lets you detect a stalled sync job — if this is more than ~24h old on every row, something's wrong |

**`contribution_days`** — one row per calendar day (full 365-day window,
including zero-commit days — see model docstring for why).

| Field | Purpose |
|---|---|
| `day` | Primary key — the date itself |
| `commit_count` | Raw count for that day |
| `intensity_level` | GitHub's own 0-4 bucketed intensity from the contribution calendar API — use directly for heatmap coloring rather than re-deriving quartiles client-side |

### 1.3 Migration

```bash
cd backend
alembic revision --autogenerate -m "add repo_stats and contribution_days tables"
alembic upgrade head
```

Double-check the autogenerated migration creates `languages` as a JSON/
JSONB column — autogenerate sometimes needs a nudge on JSON vs JSONB;
prefer JSONB for query performance if you ever filter on language keys.

### 1.4 Definition of done for Phase 1

- [ ] `repo_stats` and `contribution_days` tables exist after migration
- [ ] You can manually insert one row into each and query it back
- [ ] `github_repo_id` uniqueness constraint actually rejects a duplicate
      insert (sanity-check the upsert key works before the sync job
      depends on it)

## Phase 2 — Sync Job (next)

**Goal:** A scheduled background job that pulls fresh data from GitHub and
writes it to Postgres + Redis, so the public API never talks to GitHub
directly.

### 2.1 New pieces

```
backend/app/github/
├── client.py          # authenticated GitHub GraphQL client
├── sync.py              # orchestrates: fetch -> upsert Postgres -> write Redis cache
└── scheduler.py           # APScheduler job registration
```

### 2.2 Why GraphQL over REST here

GitHub's GraphQL API can fetch repos, their language breakdowns, and your
contribution calendar in a small number of queries — versus REST, which
needs a separate request per repo for languages and another entirely
different endpoint for contributions. Fewer round trips, and well within
even the unauthenticated rate limit, let alone the 5,000/hour authenticated
one.

### 2.3 Auth

- A fine-grained personal access token, scoped to read-only repo access
  (and read-only contribution data, which is account-level, not
  repo-scoped).
- Store as `GITHUB_TOKEN` in backend env vars — never in frontend code or
  committed anywhere.
- This is a single-owner dashboard (your data only), so a PAT is the right
  call over building an OAuth flow — there's no second "user" who needs to
  authorize anything.

### 2.4 Scheduling

- APScheduler running in-process with FastAPI (no separate worker
  service needed at this scale) — register a job that runs every 4-6
  hours.
- Also expose a manual `POST /api/admin/github/sync` (Clerk-protected,
  same pattern as `/admin/reindex`) so you can force a refresh after
  pushing something you want reflected immediately, rather than waiting
  for the next scheduled run.

### 2.5 What the sync job does, in order

1. Query GitHub GraphQL for your repos (stars, forks, languages, fork/
   private flags, timestamps) and your contribution calendar (daily counts
   and intensity levels, last 365 days).
2. Upsert into `repo_stats` (by `github_repo_id`) and `contribution_days`
   (by `day`) — full overwrite of the 365-day window each run, since it's
   cheap and avoids drift.
3. Compute the aggregate summary the frontend actually needs: total
   stars, current streak, total commits (trailing 12mo), combined language
   percentages across featured repos.
4. Write that aggregate as one JSON blob to Redis under a fixed key (e.g.
   `github:dashboard:v1`) with a TTL of ~8 hours (a bit longer than the
   sync interval, so a single missed run doesn't cause a cache miss).

### 2.6 Definition of done for Phase 2

- [ ] Running the sync job manually populates both Postgres tables
      correctly
- [ ] Re-running it updates existing rows rather than duplicating them
- [ ] The Redis key exists afterward and contains the expected aggregate
      shape
- [ ] The scheduled job actually fires on its interval (verify via logs,
      don't just trust the config)

## Phase 3 — Public API (after Phase 2)

**Goal:** `GET /api/github/stats` — fast, unauthenticated, never touches
GitHub directly.

### 3.1 Behavior

- Read the aggregate JSON from Redis. If present, return it as-is — this
  should be the overwhelming majority of requests.
- If Redis is cold (e.g. right after a deploy, before the first sync job
  run), fall back to aggregating directly from Postgres on the fly —
  slower, but correct, only happens in that narrow window.
- No auth required — this is public-facing data by design, same trust
  level as the rest of your portfolio content.

### 3.2 Response shape (draft)

```json
{
  "summary": {
    "total_stars": 142,
    "total_repos": 18,
    "current_streak_days": 12,
    "top_languages": [{"name": "Python", "percent": 47.2}]
  },
  "contribution_calendar": [
    {"day": "2025-06-21", "commit_count": 3, "intensity_level": 2}
  ],
  "repos": [
    {"name": "...", "stars": 24, "language": "Python", "url": "..."}
  ],
  "last_synced_at": "2026-06-20T08:00:00Z"
}
```

Exact shape can flex once you see what the frontend actually needs — treat
this as a starting draft, not a contract to defend.

### 3.3 Definition of done for Phase 3

- [ ] Endpoint responds in well under 100ms on a warm Redis cache
- [ ] Killing Redis and hitting the endpoint still returns correct data
      (via the Postgres fallback), just slower
- [ ] Response includes `last_synced_at` so the frontend can show
      "updated X hours ago"

## Phase 4 — Frontend (after Phase 3)

**Goal:** Homepage teaser + full `/github` page, both consuming the same
endpoint.

### 4.1 New pieces

```
frontend/
├── app/github/page.tsx          # full dashboard page
└── components/github/
    ├── GithubSummaryStrip.tsx     # homepage teaser
    ├── ContributionHeatmap.tsx      # full 12-month grid
    ├── LanguageBreakdown.tsx          # chart/bar of language percentages
    └── RepoCard.tsx                     # individual repo display
```

### 4.2 Design notes

- Matches your existing dark/glassmorphism theme — stat cards with the
  same glow effects used elsewhere, not a visually distinct "dashboard
  mode" that feels bolted on.
- Heatmap: either hand-roll an SVG grid (full control, matches your theme
  exactly) or adapt an existing open-source contribution-graph component —
  hand-rolling is reasonably small given `intensity_level` is already
  computed server-side, so this is mostly a styled grid of colored squares.
- Use Next.js ISR (revalidate every few hours, matching the sync
  interval) rather than client-side fetching — keeps the page fast and
  avoids a loading flash for what is, after all, slowly-changing data.

### 4.3 Definition of done for Phase 4

- [ ] Homepage strip shows accurate live totals and links to `/github`
- [ ] Full page renders the heatmap, language breakdown, and repo list
      correctly
- [ ] Page handles the "first ever sync hasn't run yet" empty state
      gracefully, not with a broken/blank dashboard
